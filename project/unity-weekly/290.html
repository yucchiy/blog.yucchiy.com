The path to a single render pipeline in Unity 7

The path to a single render pipeline in Unity 7 - Graphics Product Updates - Unity Discussions

Unity 7でレンダーパイプラインをURPに一本化する方針と、Built-In Render PipelineとHDRPの非推奨化および削除のスケジュールを説明するディスカッションです。

まず、Unity 6.7 LTSにてURPに入る機能として、Ground Truth Ambient Occlusion（GTAO）、Screen Space Reflections（SSR）、AgX Tonemapper、on-tile post processing、NVIDIA DLSS 4.5 Super Resolution、リアルタイムのSurface Cache Global Illumination、Unified Ray Tracing API、WebAssembly64によるWebGPU対応を挙げています。 詳細はUnity 6.7 betaのグラフィックス更新のスレッドとUnite Seoulの基調講演を参照するよう案内しています。

また、Unity 7.0のURPでは物理ライトユニット、自動露出、ダイナミックスカイが新しいライティング基盤になり、2027年の7.xサイクルでは新しいマテリアル、リフレクションプローブの改善、シャドウの進化、ボリュメトリックフォグ、Unity Neuralによる最適化、レイトレーシングベースのライティング効果を予定しているとのことです。

Built-In Render Pipelineは、Unity 7.0でobsoleteになり削除されるとのことです。 6.7 LTSのライフサイクルである2028年末まではフルサポートされ、Extended Supportでは2029年まで使える予定です。

URPにはBuilt-Inと同一のQuadratic Light Falloffが入り、Unity 6.7（6000.7.0b3以降）では Window > Analysis > Project Auditor から移行ウィザードを使えるとしています。 関連ドキュメントとしてMigrate to URP、Project Auditor、Render Pipeline Converterを紹介しています。。

HDRPは、Unity 7.0でdeprecatedになりますが、最初のUnity 7 LTS（2027年末の見込み）までフルサポートされる予定とのことです。 そのLTSのサポート期間により2029年まで、さらにExtended Supportでは2030年まで利用でき、その後はobsoleteになり削除されます。

移行手順はMigrating from HDRP to URPを参照するよう案内しており、非推奨化と削除の時期を示すタイムラインも掲載しています。

DirectX Shader Compiler support for DX12

DirectX Shader Compiler support for DX12 - Graphics - Unity Discussions

Unity 6.6でDX12向けにDirectX Shader Compiler（DXC）が公式サポートされたことを紹介するディスカッションです。

  • Configuring the target compiler with Shader Build Settings
    • 従来のshader model 6のpragmaでシェーダー単位に指定する方法に加え、プロジェクト設定で互換性のある全シェーダーをDXCでコンパイルできるようになった
      • File > Build Profiles でWindowsのビルドプロファイルを作り、Add Settings > Graphics Settings の Shader Compiler Backend Selection を DirectX12 Shader Compiler (DXC) にすることで利用できる
    • UNITY_DEVICE_SUPPORTS_NATIVE_16BIT を宣言すると half 型を明示的な16ビット型 float16_t に変換し、レジスタ使用量の削減につながる
    • Shader Model 6のwave intrinsicsにより、同じwave（warp）内のスレッドがgroup shared memoryを経由せずにデータを共有できるように
      • 32スレッドのwaveに処理を分散する WaveGetLaneIndex() や WaveActiveSum() のような関数をcompute shaderで使える
    • NVIDIA Nsight Graphicsのような最近のGPUプロファイラと互換性があり、HLSLソースのライブデバッグやシェーダーのフレームグラフを使える
  • Platform support
    • 現時点ではDirectX12を使うWindowsビルドターゲットに限られる
  • Guidelines and limitations
    • DX9/10/11向けの古いHLSLは修正が必要になることがあり、Porting shaders from FXC to DXCを参照するよう案内している
    • DXCはDX11とは互換性がない

ドキュメント（Compile shaders with the DirectX 12 compiler）にて詳細が確認できます。試したうえでのフィードバックを求めています。

[INFO] iPadOS 27 & SDK 27 adaptability changes & iPhone Duo updates

[INFO] iPadOS 27 & SDK 27 adaptability changes & iPhone Duo updates - Mobile - Unity Discussions

SDK 27でビルドしたiPadOS 27アプリにおける UIRequiresFullScreen の扱いの変更と、折りたたみ端末iPhone Duoへの対応状況を知らせるディスカッションです。

Appleは2027年4月下旬までに全アプリへSDK 27でのビルドを求める見込みとしています。

  • What’s changing
    • iPadOS: iPadOS 26から非推奨の UIRequiresFullScreen を、SDK 27でビルドしたアプリでは尊重しなくなり、動的なリサイズと向きの変化に対応する必要がある
      • SDK 26 / 27とフラグの有無による挙動の差を紹介している
      • SDK 27では、iPadの向きがアプリの許可する向きと異なる時に横倒しや上下逆に描画される
        • Appleが文書化していない挙動としている
    • iPhone Duo: 複数画面と並列マルチタスクに対応する初のiOS折りたたみ端末で、外側画面のフルスクリーン、内側画面のフルスクリーン、並列マルチタスクの3構成を持つ
      • 外側画面は通常のiPhone、内側画面はiPadのように振る舞う
      • 側面（自撮りカメラ）と下部にsafe areaの除外領域がある
  • What projects may be affected
    • iPadOS: SDK 26でビルドし UIRequiresFullScreen=true のアプリは、フラグを尊重する互換レイヤーで2027年4月まで動作する
      • SDK 27でビルドしたアプリは自動的に動的なシナリオへ入り、ゲーム向けの例外は発表されていない
    • iPhone Duo: 全iPhoneアプリが対象になり、アスペクト比が約20:9から4:3に変わり、safe areaにカメラの除外領域が加わる
  • What you should do
    • iPad: SDK 27.1でビルドしてシミュレーターと実機で確認し、2027年4月までにuGUIやUI Toolkitを動的レイアウトへ対応させる
      • 対応が難しい場合はレターボックス表示を検討する
    • iPhone Duo: 27.1のiPhoneシミュレーターで、カメラ側の除外領域を含むsafe areaの扱いを確認する
  • Known issues
    • iPhone DuoのDPIを両画面とも489と計算しているが、実際は外側430 DPI、内側460 DPIで、調査中

参考として、AppleのTN3192とGet Ready for iPhone Duo、UnityマニュアルのiOS Player SettingsとCanvas Scaler、Screen.safeArea のスクリプトリファレンスを挙げています。

キャラクターを画面内の指定領域に収めるカメラ位置の計算方法

キャラクターを画面内の指定領域に収めるカメラ位置の計算方法 - Zenn

3Dキャラクター撮影アプリで、カメラの向きと画角を固定したまま位置だけを動かし、被写体を画面内の指定した矩形領域に収めるオートフレーミングの計算方法を解説する記事です。

Renderer.bounds のAABBでは透視投影でシルエットより外側に投影されて余白が生じるため、メッシュの全頂点を使っているとのことです。 NDCで領域と余白を表し、各頂点を基準座標系へ変換して左右上下のエッジ制約値を計算し、全頂点の最小値と最大値の4つに集約したうえで、奥行きのオフセットと横縦のオフセットを反復計算なしで直接求めています。

毎フレーム追従する場合はOne Euro Filterで基準点と制約値を平滑化し、実装はCinematicCameraToolkit 0.2.0の AutoFramingSolver として公開しています。

RenderGraphのメモリ帯域削減 ― SoCのメモリ階層から実機計測まで

RenderGraphのメモリ帯域削減 ― SoCのメモリ階層から実機計測まで - Zenn

Unity 6のURPに入ったRenderGraphの効果のうちメモリ帯域の削減を、SoCのメモリ階層の説明から実機計測まで掘り下げる記事です。

モバイルSoCではDRAMとGPU内部のSRAM（タイルメモリ）の速度差が大きいことを前提に、Load / Store Actionと、RenderGraphでそれを決める AccessFlags（Read / Write / ReadWrite / Discard / WriteAll）の意味を整理しています。 そのうえで、複数のpassをタイルメモリ上で続けて実行するNativeRenderPassのマージ条件（AddRasterRenderPass であること、解像度とMSAAサンプル数の一致、Textureとしてサンプリングしないこと）、InputAttachment、FrameBufferFetch、Memorylessを、RenderGraph Viewerでの確認方法とともに解説しています。

計測はUnity 6000.3.6f1とURP 17.3.0のURP 3D Sample Gardenを、iPhone 11 Pro MaxでDeferredのMobile_Low_Rendererを使って行っています。

Disable Pass Merging のオンオフをXcodeのGPU Frame Captureで比較すると、マージ時はG-BufferがMemorylessになってDRAMの24.45 MiBが不要になり、GPUの書き込み帯域が28%、読み込み帯域が25%減ったものの、ALUが律速のためGPU時間は変わらなかったとしています。 パスマージの効果は時間ではなく転送量とDRAM使用量に出るため、AccessFlags を正確に宣言して AddRasterRenderPass を使うことを基本にし、細かい最適化は帯域が律速と分かってから行うよう勧めています。

Unity 6.7で追加されるEntityIdTileについて

Unity 6.7で追加されるEntityIdTileについて - Qiita

Unity 6.7で追加される、TilemapへのTile設定のパフォーマンス改善を目的としたEntityIdTileを紹介する記事です。

EntityIdは32ビットの InstanceID に代わる64ビットの EntityId 構造体でUnity Objectを識別するもので、EntityIdTileは GetTileData でデータを渡す従来の Tile と違いUnity JobsとBurstでTileからデータを取得できます。

Inspector、Tile Palette、Tilemap APIの基本的なワークフローは同じで、2D Tilemap Extras 10.0.0ではTile Paletteの設定でEntityIdTileと従来のTileのどちらを作るかを選べ、Window > 2D > Tile Asset Converter で既存のTile Assetを変換できます。 Tilemap上の全TileがEntityIdTileBaseから派生している必要があり、混在するとJobs / Burstを使わない処理にフォールバックするとのことです。

MagicOnionで弾幕エンジンFsBulletML2を使おう — UnityとGodotは受けた座標を描画するだけ(おまけJev) - Zenn

2013年のF#製弾幕エンジンFsBulletMLをリブートしたFsBulletML2を、MagicOnionのサーバー上で動かし、UnityとGodotのクライアントは受け取った座標を描画するだけにする構成を解説する記事です。

旧設計ではエンジンがフロント側のオブジェクトを途中で呼び返す必要がありましたが、新設計では1フレーム進める関数1本のインターフェイスになったためサーバーに置けるようになったとしています。

StreamingHubは弾のIdと座標、向き、種別だけを配信し、ゲームループは PeriodicTimer で駆動するRoomがHubの外で回し、当たり判定は下りと上りの通信量や複数プレイヤーの観点からサーバー側で一元管理しています。 エンジンのコアはReader / State / Writerを1つに畳んだSimモナドで駆動し、旧エンジン比で5倍の性能とヒープ確保47%削減を達成したほか、Cloudflare Workers AIのモデルで弾幕の特性を返させてBulletMLを組み立てるJevと、ブラウザで動くDanmaku Galleryも紹介しています。

Shaderlyn - 大規模開発に対応するシェーダー静的解析ツール

Shaderlyn - 大規模開発に対応するシェーダー静的解析ツール - Zenn

ShaderLabとHLSLを構文解析し、プリプロセッサの条件分岐を考慮して問題を指摘する静的解析ツールShaderlynを紹介する記事です。

#if や #pragma multi_compile の全組み合わせを試すのは現実的でないため（Unity 6000.3.0f1のHDRPの LayeredLitTessellation.shader では118シンボル）、トークン列に条件を付けて解析する方式を採り、上限を超えた分だけ組み合わせを試して解析しきれない時は診断を出します。 これにより、ある分岐の組み合わせでだけ未宣言になる変数や、ShaderLabのプロパティとHLSLの宣言との型の不一致を検出でき、Roslyn風のAPIでプロジェクト固有のルールも書けます。

配布はCLI（GitHub ReleaseとNuGet）と、ホバー、リネーム、定義ジャンプ、参照検索に対応するVSCode拡張で、出力はjson、github、sarif形式を選べるためCIに組み込めます。 v0.1.1でAPIはv1まで不安定であり、Unity以外のシェーダー環境は今後の課題としています。

Unity6.6からFast Enter Play Mode(ドメインリロード無し)がデフォルトになって再生が爆速になった話と、staticな値がリセットされない場合の対処法【Unity】

Unity 6.6の新規プロジェクトでEnter Play Mode Settingsの既定が「Reload Scene only」になり、ドメインリロードなしで再生が始まるようになったことと、static値が持ち越される時の対処法を紹介する記事です。

既存プロジェクトの設定は自動では変わりません。

持ち越されるstatic値は、Unity 6.5で追加された [OnEnteringPlayMode] と [AutoStaticsCleanup] で再生開始時に初期化でき、Project AuditorのRoslyn Analyzersで対象を洗い出せるとのことです。

UnityでなぜC# 10以降を使うライブラリが動くのか

UnityでなぜC# 10以降を使うライブラリが動くのか - Zenn

Unity 6.6の公式対応がC# 9.0であるにもかかわらず、ZLogger、R3、MemoryPackのようなC# 10以降の機能を使うライブラリが動く理由を、コンパイラ、BCL、ランタイムの3層に分けて解説する記事です。

同梱のRoslyn 4.3.1はC# 10まで（preview でC# 11の一部も）コンパイルでき、構文糖はコンパイラだけで、init のような機能はPolyfillで補えるため古いランタイムでも動くと説明しています。

ランタイムの対応が必要な機能は別に確認が要るとし、EditorとIL2CPPでの動作確認結果と csc.rsp の設定方法もまとめています。

Unity 6.3のメモリ解放で気を付けること：GC・Destroy・Disposeの使い分け

Unity 6.3のメモリ解放で気を付けること：GC・Destroy・Disposeの使い分け - Zenn

Unity 6.3 LTS、Addressables 2.10系、Collections 2.6系を対象に、メモリの解放方法は型ではなく取得方法で決まるという原則で、null 代入、Destroy、Dispose の役割を整理する記事です。

renderer.material を読むだけで複製が生まれる所有権の問題、Addressablesのロードと Release の対応、UnloadSceneAsync や Resources.UnloadUnusedAssets() で消えないもの、NativeArray の構造体コピーが同じメモリを指すこと、RenderTexture.Release() と GetTemporary() の返却、イベント購読やプールが参照を残すケースを扱っています。

検証は同じ状態へ繰り返し戻してMemory Profilerでスナップショットを比較する手順を勧めています。
